# 機能仕様書

アーキテクチャ・技術構成は [README.md](../README.md) を参照。本書は画面ごとの機能・業務ルール・UI/UX上の決定をまとめる。

## 業務フロー

```
① 従業員を登録する（/employees）
  ↓（任意）
② 勤務ルールを設定する（/settings）
  ↓
③ 月を開く（TOP /）
  ↓
④ 希望休入力（/plans/:planId/leaves）
  ↓
⑤ 必要人数設定（/plans/:planId/headcount）
  ↓
⑥ シフト表で編集・自動割当・出力（/plans/:planId/shifts）
```

①だけが必須の前提条件。②は任意（未設定なら該当する違反チェックがスキップされる）。④⑤⑥は同じ月内で行き来しながら進める想定で、順序の強制はない。

## 画面ごとの仕様

### TOP（`/`）

- 「はじめに」チェックリスト：①従業員登録・②勤務ルール設定（任意）・③月を開く、の3項目。完了済みの項目は緑チェックになるが、行自体は消えない（常時参照できるようにするため）。
- 店舗名（設定済みの場合）はH1の下にサブタイトルとして表示。H1自体は常に「シフト作成」で固定（店舗名で丸ごと置き換えない — 店舗名を設定するとページの現在地が分からなくなる問題があったため）。
- 「月を開く/新規作成」フォームで年月を指定して開く。存在しない年月なら新規作成される（`UPSERT_PLAN`）。
- 「シフト計画一覧」に過去に開いた月が一覧表示される（完了/未完了のステータス管理はしていない、単なる存在一覧）。

### 従業員（`/employees`）

- 新規登録フォーム：氏名（必須）・役割（任意、フリーテキスト）・雇用形態（正社員/パート・アルバイト）。
- Excelから一括登録：テンプレートDL → 記入 → 読み込み。氏名が空の行、および`※`で始まる行（注意書きの誤混入対策）はスキップされる。
- 登録済み従業員は1人1カードで氏名・役割・雇用形態・在籍中フラグを編集可能、削除もできる（一覧性より編集のしやすさを優先した設計。人数が多い場合の閲覧性は今後の検討課題）。
- 在籍中フラグをOFFにした従業員は、以降の希望休入力・必要人数設定・シフト表に出てこない（`activeEmployees()`セレクタで絞り込み）。既存のシフト割当データ自体は残る。
- 従業員登録後、「①（任意）勤務ルールを設定する」「②TOPでシフト計画を開く」の2ボタンで次のステップに誘導する。

### 設定（`/settings`）

- 店舗名：入力すると自動保存（Excel出力の見出しに使われる）。
- 勤務ルール：最大連続勤務日数・週間最大労働時間（共に任意、未設定＝上限なし）。店舗名と同様、入力すると自動的に反映される（保存ボタンなし）。
- 下部に「TOPでシフト計画を開く」ボタンで次のステップへ。

### 希望休入力（`/plans/:planId/leaves`）

- 従業員×日付のチェックボックスグリッド。チェック＝その日その従業員が休みを希望、を意味する。
- チェックのオン/オフごとに自動的に反映される（`REPLACE_LEAVES_FOR_PLAN`、その月の希望休を丸ごと置き換え。保存ボタンなし）。
- Excelテンプレートは**登録済みの全従業員名があらかじめ入った状態**でダウンロードされる（希望休入力はそもそも従業員登録済みが前提のため、ゼロから名前を手入力させない設計）。取り込み時、テンプレートの氏名と現在の登録名が一致しない行は「未登録の氏名」としてスキップされ、メッセージで通知される。

### 必要人数設定（`/plans/:planId/headcount`）

- カレンダー形式。日付ごとに複数の時間帯（例：早番・遅番）× 必要人数を設定できる。
- 「一括設定」：期間・曜日で絞り込んで、同じ時間帯・人数をまとめて設定（既存の設定は上書き）。
- カレンダーの「+」から日付ごとに個別追加も可能。時刻入力は分の選択が完了した時点で確定・ピッカーを閉じる（既存枠の編集時は枠ごと閉じる、追加フォームでは人数入力が残るためピッカーの見た目だけ閉じる）。

### シフト表（`/plans/:planId/shifts`）

- 従業員×日付のマトリクス。セルをクリックすると勤務時間/有休/休を選択するポップオーバーが開く。
  - ポップオーバーは`position: fixed`でテーブルの外（`document.body`直下）にポータル表示。画面下にはみ出す場合は上側に反転表示。テーブルのスクロールでは追従せず、スクロールが起きると自動的に閉じる（Escapeキーでも閉じる）。
- 「1人分をまとめて登録」：1人の従業員について、日付範囲・曜日・勤務時間を指定して一括登録（複数人へのまとめて登録には非対応）。
- 「自動割当」：必要人数・希望休・勤務ルールをもとに、たたき台となるシフトを生成する（アルゴリズムの詳細は下記「自動割当ロジック」）。既存の割当は上書きされる。
- 「Excelに出力」：本名入りのExcelファイルとしてダウンロード（店舗名・日付ごとの必要人数・従業員ごとの勤務時間・日別/従業員別の合計時間を含む）。
- 違反一覧：下部にリアルタイムで表示（下記「違反判定ルール」参照）。

## 業務ルールの定義

### 必要人数（`HeadcountRequirement`）

`{ date, startTime, endTime, requiredCount }` の組。同じ日に複数設定でき、それぞれ独立に扱われる（例：早番と遅番はマージされず別々の枠として必要人数・自動割当の対象になる）。

### 勤務ルール（`WorkRule`）

- `maxConsecutiveWorkDays`：これを超えて連続勤務日が続くと違反（`null`＝上限なし）。
- `maxWeeklyHours`：日曜始まりの1週間で、この時間を超えて勤務時間が割り当てられていると違反（`null`＝上限なし）。

### 違反判定ルール（`checkViolations`）

| 種別 | 内容 |
|---|---|
| `unmet_leave_request` | 希望休を出した日に勤務(`work`)が割り当てられている |
| `max_consecutive_days` | 連続勤務日数が`maxConsecutiveWorkDays`を超えている |
| `max_weekly_hours` | 週間勤務時間が`maxWeeklyHours`を超えている（日曜始まり） |
| `understaffed_slot` | ある必要人数枠について、その時間帯を完全に覆う勤務(`work`)の人数が`requiredCount`未満 |

`understaffed_slot`の判定は「その枠の開始〜終了を割当のstartTime〜endTimeが完全に包含しているか」で数える（部分的に重なるだけでは数えない）。

### 自動割当ロジック（`autoAssignShifts`）

- 貪欲法（greedy）による「たたき台」生成であり、最適解を保証するものではない。
- 必要人数枠を日付→開始時刻の順にソートし、枠ごとに独立して埋めていく（同日に早番・遅番があっても別々に処理し、1つの長時間シフトにマージしない）。
- 各枠について、候補者を「これまでの合計勤務時間が少ない順」にソートし、以下の条件を満たす人から順に割り当てる：
  - その日に希望休を出していない
  - その日に別の枠へ既に割り当て済みでない（1人1日1シフトが前提）
  - 割り当てると`maxConsecutiveWorkDays`を超えない
  - 割り当てると当該週の`maxWeeklyHours`を超えない
- 必要人数を満たせなかった枠は`understaffed_slot`違反として結果に含まれる。

## 個人情報保護の境界（要点）

詳細は [README.md](../README.md#個人情報保護アーキテクチャ) を参照。本名（`PiiEmployee.name`）はブラウザのメモリ上にのみ存在し、Lambdaへのリクエスト・レスポンスの双方に一切含まれない。`Violation`型もID・enum・日付のみで構成され、「〇〇さんは希望休を...」のような文言はフロントエンドが表示直前に組み立てる（`rehydrate.ts`）。

## データの永続化モデル（要点）

無料プラン（アカウント未登録）はサーバー側に一切の永続化を持たない。ブラウザを閉じる/リロードすると「保存(ファイル)」していない変更は失われる（意図的な仕様）。有料プラン（Cognitoログイン済み）はDynamoDBへの自動クラウド保存が加わる（下記「クラウド保存（有料プラン）」参照）。

- 保存(ファイル)/読み込み：全状態（従業員・全計画のシフト・希望休・必要人数・勤務ルール）をJSONファイルとして書き出し/読み込みする、無料プランでの唯一のバックアップ・復元手段。
- 離脱時の保護：`beforeunload`でブラウザ標準の確認ダイアログを出す。ダイアログの文言自体はブラウザ仕様でカスタマイズ不可能なため、ダイアログで「キャンセル」した後（＝ページに留まった後）に画面内バナーで保存を案内する仕組みを別途用意している（`useBeforeUnloadGuard`。beforeunload発火直後にタイマーを仕掛け、実際に離脱した場合は`pagehide`でタイマーを解除、キャンセルされた場合はタイマーが発火してバナーを表示する、という一般的な検出手法による）。
- 元に戻す（Undo）：直前の状態変更を1つ前に戻せる。実装は状態全体（`AppState`）のスナップショットを`MARK_SAVED`以外の全アクション実行前に履歴として積むだけの単純なもの（直近30件まで、`AppStateContext.tsx`の`historyReducer`）。取り消したい場面が実質「一括設定（必要人数設定）」「自動割当（シフト表）」のような1回のdispatchで完結する一括操作に限られるため、ボタンはその2箇所（一括設定の隣・自動割当の隣）にのみ表示し、それ以外の画面には出さない。Cmd/Ctrl+Zでも同じUNDOアクションを発火できる（テキスト入力欄にフォーカス中はブラウザ標準のテキスト編集undoを優先し、こちらは発火しない）。redo（やり直し）は無い。

### クラウド保存（有料プラン）

DynamoDBはシングルテーブル設計（`accountId`＝Cognitoの`sub`をパーティションキー、`sk`をソートキー）で、アカウントごとの状態を1個の巨大なJSONではなく用途別に正規化して保存する。

| `sk` | 内容 |
|---|---|
| `MASTER` | 店舗名・従業員一覧・勤務ルール・作業種別マスタ |
| `MONTH#<planId>`（例: `MONTH#2026-09`） | その月の計画（`MonthlyPlan`）・必要人数・希望休 |
| `DAY#<date>`（例: `DAY#2026-09-01`） | その日の割当シフト・分刻みタスクセグメント（実データがある日付のみレコードが存在する） |
| `ACCOUNT` | 有料/無料プランの状態（Stripe Webhookが書き込む。`/state`のGET/PUTからは常に除外される） |

フロントエンドの`AppState`はこれまで通り1つのオブジェクトのまま（reducer・selector・画面コンポーネントは無変更）で、`apps/web/src/lib/cloud/records.ts`の`toRecords`/`fromRecords`が保存時・読み込み時にだけ分割・復元する。自動保存（`useCloudSync`）は変更があったレコードだけを差分検出して`PUT /state`に送り（`DynamoDBTransactWriteItems`で原子的に書き込み）、レコードごとに`updatedAt`を使った楽観的ロックを行う（別端末・別タブでの上書き事故を検知し、競合時はUIで「上書き保存」か「相手の内容を読み込む」を選べる）。

## UI/UXに関する主な設計判断

ブラインドテスト（サブエージェントによる第三者視点の操作テスト）を複数回実施し、見つかった問題への対応として以下を決定した。

- **ナビゲーション**：ロゴ+メニューと右側の保存系ボタンをそれぞれ一塊として`flex-wrap`させ、幅が狭い時に個々のリンクがバラバラに折り返さないようにしている。
- **各画面末尾の次ステップ誘導**：従業員登録後・設定変更後にそれぞれ次の画面へのボタンを明示（以前はTOPへの地味なテキストリンクのみで、勤務ルール設定への導線が無かった）。
- **保存の文言**：「保存(JSON)」ではなく「保存(ファイル)」と表記し、内部形式（JSON）という開発者用語を前面に出さない。ただし「ファイルとして保存される」という実態は正直に伝える。
- **一括操作系ボタンの命名**：「一括作成」→「1人分をまとめて登録」（実態が1人分の複数日一括登録であり、複数人への一括登録ではないことを明示）。
- **エクスポート系ボタンの完了フィードバック**：クリック後に無反応に見える問題があったため、成功メッセージを追加。
- **モーダル/ポップオーバーの背景**：一括登録モーダルは背景を暗転させ、背後のテーブル・違反一覧が前面にあるように見えて紛らわしい問題を解消。z-indexはテーブルの`sticky`ヘッダー（z-30）より確実に高い値（z-50）にしている。
